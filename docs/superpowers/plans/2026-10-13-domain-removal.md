# Domain-Scoped Removal Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Safely remove individual add-on websites and subdomains with understandable confirmation, durable progress, retained databases/backups, and two live acceptance passes on nakpanel.com.

**Architecture:** Add a dedicated removal service to the existing provisioning manager, backed by PostgreSQL operations and ID-only River jobs. A scoped agent teardown uses durable identity fences and checkpoints; shared configuration is regenerated from surviving intent. The existing templ shell and shared JavaScript dialog/request helpers provide enhanced and non-JavaScript flows.

**Tech Stack:** Go, PostgreSQL, goose, River, templ, embedded CSS/vanilla JavaScript, stdlib HTTP, Linux systemd/nginx/BIND/Stalwart/ProFTPD/Podman.

**Spec:** `docs/superpowers/specs/2026-10-13-domain-removal-design.md` (approved 2026-10-13).

## Global Constraints

- Databases and existing backups are kept by default. No backup is forced or silently created for the default operation.
- Permanent removal is a distinct action, not suspension or disabling hosting.
- The primary website, configured panel hostname, and sites hosting configured server-wide mail/FTPS/hostname dependencies cannot be individually removed.
- Never delete the subscription home, reset its quota, kill all processes for its UID, prune shared container state, or call subscription teardown.
- Cross-tenant/provider/support-scope lookups return 404. CSRF protects every reservation and retry.
- Removal snapshots contain non-secret IDs and server-derived identities only.
- Operation states are `queued`, `waiting`, `running`, `failed`, and `completed`; site removal states are `none`, `queued`, `removing`, and `failed`.
- Keep domains reserved and counted against allocation until removal is complete. Failed cleanup remains visible and counted.
- Use readable 14px fields, an 18px dialog title, wrapped hostnames, and 44px mobile action targets.
- Poll a scoped operation status endpoint with bounded requests and a five-minute foreground wait.
- Preserve standard HTML POST/303/progress-page behavior and enhanced 202 JSON responses, existing routes, and support prefixes.
- No current live resource is implicitly selected for deletion. Live QA uses explicitly identified fixtures and confirmation before removal.
- Keep existing production content, server hostname SSL, mail, and unrelated subscriptions intact; do not reset or reboot the public server for this feature.

## Review Focus

- A previously captured parent-zone DNS or global mail/FTPS snapshot must not reintroduce a removed child while preserving unrelated domains (Tasks 4, 6, 7).
- An agent cleanup succeeded but PostgreSQL finalization failed; retry must finish once without deleting a replacement using the same hostname (Tasks 4, 7).
- A staging operation references the target as its destination, not its source; it must be fenced and must not expand the destructive scope to its surviving source (Tasks 1, 5, 7).
- A resource or child appeared between preview and confirmation; removal must demand a fresh preview instead of silently deleting it (Tasks 2, 3).
- A lost response or expired browser session must not replay deletion, invent success, lose the operation, or send the user to a deleted site (Task 8).

## Shared Contracts

Create `internal/types/site_removal.go` for these shared, versioned contracts:

- `SiteRemovalPreview`: `SiteID`, `SubscriptionID`, `CustomerID`, `ParentSiteID`, `PrimarySiteID` (`int64`); canonical `Domain`, `Kind`; `Allowed`, `RequiresHostnameConfirmation`; `BlockedReasons []string`; typed `Snapshot SiteRemovalSnapshot`; `Digest string`; optional `Operation *SiteRemovalOperation`.
- `SiteRemovalSnapshot`: `SchemaVersion int` (1); immutable target identities and exact IDs for PHP apps/workers/deployments, WordPress, Git, OCI generations, tasks, access, mail/webmail, DNS, statistics, databases and backups. Sorted slices only; no credentials, environment, arbitrary paths, or command text. Each item retains its site/subscription association; DNS records retain their zone and owner-site identity.
- `SiteRemovalSite`: positive `SiteID`, `SubscriptionID`, `CustomerID`, `ParentSiteID`, canonical `Username`, `Domain`, and validated PHP version. Physical paths and service names are not fields.
- `SiteRemovalDatabase`: `ID`, `SiteID`, `SubscriptionID`, name, provenance, `DeletionEligible`, `IneligibleReason`, and server-selected `RecoveryBackupID` when required; no password or decrypted credentials.
- `RemoveSiteReq`: `SiteID int64`, `RequestID`, `PreviewDigest`, `ConfirmDomain string`, `AcknowledgePermanent`, `IncludeChildren bool`, `DeleteDatabaseIDs []int64`. An empty database list always means keep all databases; there is no backup-deletion or arbitrary return-URL field.
- `SiteRemovalOperation`: durable ID, request ID, scope/actor/target labels, approved snapshot/choices/revision, state, stage, completed checkpoints, bounded sanitized error, and creation/update/completion times. Never serialize the private approval token or agent configuration secrets.
- `TeardownSiteReq`: `OperationID`, `Revision`, `SubscriptionID`, approved `Snapshot`, `Stage SiteRemovalStage`, and explicit selected database identities. The agent validates all relationships and derives all paths.
- `TeardownSiteResult`: operation/revision, completed checkpoint names, safe resource IDs and bounded errors; no raw command output.

Define `SiteRemovalStage` values `waiting`, `stop_services`, `remove_hosting`, `reconcile_shared`, `finalize`, `completed`. Central helpers validate states/transitions and sanitize failure strings to one line, at most 512 UTF-8 bytes. Persist stage outcomes monotonically; an RPC timeout cannot mark a checkpoint complete.

Implementation-private interfaces live beside the service that consumes them:

Its usage adapter makes only bounded read-only calls with server-derived identities and paths; unknown inventory conservatively requires hostname confirmation. The concrete shared-services implementation is `SQLSiteRemovalSharedServices` in Task 6. `SiteTeardownOptions` has configured `SitePathConfig`, `CommandRunner`, `*MariaDBEngine`, `*SiteIdentityRegistry`, `*MailProvisioner`, and fixed state-root strings; do not infer these roots from an RPC payload.
