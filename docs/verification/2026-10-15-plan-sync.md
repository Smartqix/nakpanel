# Plan Synchronization Verification

Initial verification revision: `d86afe5`. At that point the production schema
remained `20261013000053`. The mail/DNS rollout subsequently advanced it to
`20261015000055`.

The original failure was a contradictory contract, not a missing plan update:
plan 5 enabled WordPress Toolkit but allowed zero installations. The two
synchronized subscriptions had correctly inherited that zero limit.

With the approved allowance of five installations:

- Desktop pass: 1440 x 1000, plan revision 3, subscriptions 3 and 12 updated.
- Mobile pass: 390 x 844, plan revision 4, subscriptions 3 and 12 updated.
- Both passes validated rejection of enabled WordPress with zero capacity,
  saved through the panel review form, and waited for snapshot and service
  convergence. Neither pass reported a failed subscription.
- Read-only SQL confirmed both subscription snapshots and system accounts
  were in sync after revision 3. The second panel status check confirmed
  revision 4. No WordPress installation or existing website was deleted.

Visual review found that the new synchronization rows accidentally inherited
an icon-column grid. A dedicated two-column row style was added with a
regression test and deployed in the subsequent verified rollout.

After the final backend deployment (`3bd9d67`), read-only checks reconfirmed
WordPress permission and the five-installation limit on plan 5 and subscription
snapshots 3 and 12. Both subscription system accounts were still `in_sync`.

This verifies plan propagation and the allowance, not installation of five
new production WordPress instances.
